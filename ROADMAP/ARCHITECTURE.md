# Архитектура Jasta

Актуально на 2026-11-20. Документ фиксирует согласованный план развития существующего репозитория, а не реализованные возможности.

## Назначение и стек

Jasta размещает контент статических сайтов, управляет версиями и настройками сайтов через локальную админку, а также настраивает Nginx и TLS.

- Backend: Go 1.26.8 и существующий `go.osspkg.com/goppy/v3` v3.2.3.
- Хранилище управляющих данных: SQLite, через Goppy ORM-плагин. CGO допускается.
- Frontend: React, TypeScript, Tailwind CSS 4 с `@tailwindcss/vite`, Vite, Oxlint и pnpm.
- Backend transports: Goppy JSON-RPC для команд, WebSocket для прогресса, отдельные multipart HTTP-маршруты для архивов.
- Поставка: Debian/Ubuntu `.deb` для amd64 и arm64, два systemd-сервиса.

## Текущее состояние репозитория

- Точка входа `cmd/jasta/main.go` запускает один Goppy-процесс с публичным API и заглушкой admin API.
- `internal/pkg/application` содержит SPA и MPA; Markdown и redirect реализации пока являются panic-заглушками.
- Сайты сейчас обнаруживаются из YAML-каталога. Пример production-конфига устарел относительно текущей структуры `type/domains/root`.
- SQLite и frontend в репозитории отсутствуют. Тестовый файл есть у `internal/pkg/urlclean`.
- `.deb` уже нацелен на amd64/arm64, но описывает один бинарник и один systemd-сервис `jasta.service`.
- Текущий Nginx-конфиг проксирует запросы на `127.0.0.1:15432`.

Реализацию существующих участков следует расширять без удаления пользовательских данных и исторических релизов. Импорт поддерживаемых YAML-конфигов и отчёт по непереносимым конфигам предусмотрены отдельной задачей.

## Процессы и сетевые границы

```text
Клиенты сайтов ──HTTPS──> Nginx ──HTTP localhost──> jasta web
Браузер владельца ─HTTPS─> Nginx ──HTTP localhost──> jasta admin
                                      │
                                      ├─ JSON-RPC / WebSocket / multipart
                                      └─ сертификаты и выделенные Nginx include-файлы

jasta admin ──Unix socket: active snapshot + reload──> jasta web
```

- `jasta web` обслуживает только публичные сайты, слушает localhost и не открывает admin API.
- `jasta admin` слушает только localhost. Отдельный admin-домен проксируется Nginx по HTTPS.
- SQLite принадлежит `jasta admin`; `jasta web` не подключается к базе. Admin передаёт активный снимок конфигурации и релиза через локальный Unix-сокет. Web проверяет снимок и обновляет in-memory маршрутизацию без перезапуска.
- Content-релизы хранятся как неизменяемые каталоги. Web читает активный контент; admin создаёт и переключает релизы.
- `jasta admin` имеет отдельную системную учётную запись и доступ только к требуемым каталогам. Право проверки и reload Nginx выдаётся узко; сервис не запускается от root.
- Nginx конфигурации Jasta располагаются в отдельной include-зоне. Перед reload admin выполняет `nginx -t`; ошибочная конфигурация не применяется.

## Данные и жизненный цикл релиза

SQLite хранит сайты, домены, конфигурации, снимки конфигураций, источники архивов, метаданные релизов, задания, владельца и refresh-сессии, а также данные управления сертификатами. Файлы контента и TLS-ключи хранятся отдельно от базы.

Конфигурация сайта редактируется отдельно от архива. При публикации создаётся связка «релиз контента + снимок конфигурации сайта». Проверка и сборка проходят в staging-каталоге; активный снимок меняется только после успешной сборки. Откат активирует пару из выбранного релиза и его конфигурации. Снимки учётной записи, registry-секретов и глобальных настроек TLS в rollback сайта не входят.

- Форматы загрузки: ZIP и TAR.GZ.
- Начальные лимиты: 100 МБ входного архива и 1 ГБ распакованных файлов; оба значения настраиваются.
- Все релизы сохраняются до ручного удаления; админка показывает занятое ими место.
- Загрузка по URL разрешает только внешние HTTPS-хосты. Проверяются IP-адреса после DNS-разрешения и на каждом redirect; loopback, локальные и зарезервированные диапазоны запрещены.
- Поддержка источников: HTTP Basic, Bearer и query-подпись URL. Секреты шифруются AES-GCM ключом из отдельного root-owned файла; чувствительные URL и заголовки не попадают в логи.
- Ручной backup/restore должен согласованно включать SQLite, конфигурации, все релизы, ключ шифрования, ключи JWT, данные владельца, ACME account key и TLS-сертификаты с приватными ключами.

## Модель сайтов

| Тип | Контракт |
|---|---|
| SPA | Отдаёт существующие файлы; для маршрута без отдельного файла возвращает корневой `index.html`. |
| MPA | Каталог URL отображает свой `index.html`; отсутствующая страница остаётся 404 и не превращается в SPA fallback. |
| Markdown | Front matter в YAML; `slug` обязателен и уникален, задаёт root-relative URL; `/` допускается для главной страницы. `title` и `description` необязательны. Go `html/template` создаёт HTML; статика копируется в результат сборки. Raw HTML из Markdown по умолчанию экранируется. |
| Redirect | Правило связывает домен-источник с целевым доменом; path и query исходного запроса сохраняются. Код 301 или 308 задаётся на каждом правиле. |

Для неизвестного host web возвращает явный ответ ошибки и не маршрутизирует запрос к случайному сайту.

## Admin API, вход и события

- Один локальный владелец создаётся одноразовой CLI-командой. Вход использует пароль и обязательный TOTP.
- При настройке TOTP recovery-коды показываются владельцу один раз; для восстановления доступны локальная CLI-команда сброса и одноразовые коды.
- Access JWT живёт 15 минут. Refresh-сессия обновляется и отзывается на logout; рекомендуемый максимум срока одной сессии — 7 дней.
- JWT signing material задаётся постоянно и хранится вне SQLite. Встроенное значение по умолчанию Goppy генерирует ключи в памяти; его нельзя использовать как постоянное хранилище signing keys.
- JSON-RPC обслуживает вход, настройки сайта, registry, деплои, историю/откат и управление сертификатами; защищённый `nginx.apply` генерирует только Jasta include по site domains из SQLite и root-managed admin Nginx settings. Перед атомарным apply выполняются isolated candidate и full-config `nginx -t`; при ошибке include откатывается, reload не выполняется. WebSocket передаёт прогресс сборки, скачивания, публикации, отката и получения сертификата. Multipart маршруты ограничивают размер загружаемого тела до архивного лимита.
- Секреты registry хранятся в SQLite только в шифрованном виде. Root-owned ключ доступен только `jasta admin`.

## Nginx и сертификаты

- Nginx остаётся точкой TLS termination для сайтов и admin-домена; admin генерирует только принадлежащие Jasta конфиги.
- Для локальных доменов и временного fallback Jasta создаёт самоподписанный сертификат.
- Для публичных доменов используется Let’s Encrypt через HTTP-01; wildcard-домены и DNS API не входят в план.
- ACME challenge-ответ должен быть доступен через Nginx на HTTP-порту 80; после получения или продления сертификата выполняются проверка Nginx и reload.
- Продление сертификатов автоматическое, управление challenge и ключами выполняет `jasta admin`.

## Frontend

Источник приложения планируется в `ui/admin/`; собранные Vite-файлы включаются в бинарник `jasta admin` для установки одним `.deb`. UI покрывает вход и настройку владельца, список сайтов, домены/сертификаты, конфиг, registry-источники, публикацию, прогресс, историю релизов и rollback. Низкорисковое предположение: интерфейс сначала русскоязычный, адаптивный и доступный с клавиатуры; отдельного визуального референса пользователь не задавал.

Документация Vite на дату исследования требует Node.js 20.19+ или 22.12+; для локальной сборки планировать Node.js 22.12+. Tailwind Vite-плагин соответствует согласованному `@tailwindcss/vite`; frontend bootstrap должен добавить `package.json`, lockfile и реальные команды lint/build.

## Организация кода и зависимостей

Существующие `cmd/jasta`, `internal/api/{public,admin}`, `internal/pkg/application`, `internal/pkg/config`, `internal/pkg/nginx` и `.deb.yaml` развиваются по месту. Новые зоны ответственности размещаются внутри `internal` по предметным пакетам: runtime/process, site config and snapshot, storage, deployment/release, archive, markdown builder, admin auth/API, ACME и Nginx config.

Планируемая директория `ui/admin/` содержит React/TypeScript и Vite. `ROADMAP/` хранит задачи и QA-контракты. Не вводить новую Go-библиотеку без проверки её официальных API, версии и совместимости с Go 1.26.8; go-markdown уже выбран пользователем.

### Проверенные источники

- Goppy v3: [официальная документация](https://goppy.osspkg.com/) — текущий проект уже использует v3.2.3; документация описывает серверный пул, плагины, DI и миграции.
- Goppy SQLite/auth: локальный исходный код версии v3.2.3 в module cache. SQLite-коннектор импортирует `github.com/mattn/go-sqlite3`; дефолтный locking mode — `EXCLUSIVE`. JWT default генерирует ключи в runtime. Поэтому база принадлежит только admin, а web получает снимок через UDS; JWT-ключ задаётся явно.
- SQLite driver: [mattn/go-sqlite3](https://github.com/mattn/go-sqlite3) требует `CGO_ENABLED=1` и C-компилятор. Пользователь разрешил CGO.
- Markdown: [go.osspkg.com/markdown](https://pkg.go.dev/go.osspkg.com/markdown) — отдельный Go-конвертер с `html/template` в приложении; raw HTML по умолчанию экранирован, converter ограничивает вход 16 MiB, глубину 128 и число tokens 1,000,000. Эти ограничения и лимит архива нужно согласовать для сборщика.
- ACME: [Go `x/crypto/acme`](https://pkg.go.dev/golang.org/x/crypto/acme) предоставляет операции ACME и HTTP-01 challenge helpers. В `go.mod` уже присутствует `golang.org/x/crypto` v0.53.0 как indirect; текущие pkg.go.dev docs показывают более новую версию, поэтому API проверять на версии, совместимой с Go 1.26.8.
- Challenge: [Let’s Encrypt HTTP-01](https://letsencrypt.org/docs/challenge-types/) доступен только на порту 80 и не выдаёт wildcard-сертификаты.
- Nginx: [параметры `-t` и `-s reload`](https://nginx.org/en/docs/switches.html) — `-t` проверяет синтаксис и доступность файлов; reload запускает новые workers и gracefully завершает старые.
- Frontend: [Vite guide](https://vite.dev/guide/), [Tailwind через Vite](https://tailwindcss.com/docs/installation/using-vite), [Oxlint](https://oxc.rs/docs/guide/usage/linter/quickstart.html), [pnpm](https://pnpm.io/installation). У Vite проверено требование Node 20.19+/22.12+.
