# Контекст F02 — Обслуживание типов сайтов

## Согласованные решения

- SPA fallback использует главный `index.html`; MPA разрешает каталоги и их `index.html`.
- Markdown front matter — YAML; `slug` обязателен и уникален, задаёт root-relative URL, `/` разрешён для главной страницы. `title` и `description` необязательны.
- Markdown отображается через Go `html/template`; статические файлы копируются без изменений.
- RedirectPageApplication сохраняет path/query; статус 301 или 308 настраивается по правилу.
- Неизвестный домен получает явную ошибку и не сопоставляется случайному сайту.

## Состояние репозитория

- `internal/pkg/application/spa.go` и `mpa.go` уже обслуживают часть статических файлов, но не соответствуют целевому точному контракту полностью.
- `internal/pkg/application/mda.go` и `rpa.go` пока содержат panic-заглушки.
- Общие конфигурационные структуры живут в `internal/pkg/config`; действующий production YAML пример устарел.
- F02-T01 нормализует host и записи доменов одинаково: убирает завершающую точку и валидный порт, приводит ASCII DNS-имена к нижнему регистру и приводит IP-адреса к канонической записи. Unicode-домены задаются в ASCII A-label/punycode форме. Некорректный host получает HTTP 400, неизвестный нормализованный host — 523.
- Каждый service регистрируется в runtime только после проверки всех доменов; конфликт, включая совпадение после нормализации, отклоняет весь service или snapshot и не меняет активное состояние. Тот же путь регистрации применяется к YAML на старте и снимкам reload.
- F02-T02 использует общий безопасный путь выдачи файла через `os.Root`: URL traversal сегментом `..` и обратный слеш отвергаются, каталоги не выдаются как файлы. SPA сначала отдаёт существующий файл, missing asset/system path получает custom 404, неизвестный путь использует корневой index. MPA сначала отдаёт существующий файл, затем ищет `Pages.Index` внутри пути каталога; отсутствующая страница получает custom 404.
- F02-T03 принимает для redirect-правила нормализованный домен, абсолютный исходный path, абсолютный HTTP/HTTPS target без credentials/query/fragment и обязательный `status_code` 301 или 308. Для одного домена применяется наиболее длинный совпавший path-prefix с границей сегмента; к path target добавляется оставшийся suffix, а исходные query и пустой завершающий `?` сохраняются. Правила и полный набор сайтов проверяются на циклы при сборке snapshot и при старте web.
- Redirect-конфигурация не содержит query целевого URL: query берётся из запроса. Path-prefix `/` соответствует всем путям; если ни одно правило домена не совпало, RPA отвечает 404.
- F02-T04 использует `source/` как дерево входа и `root` как каталог собранного сайта; эти каталоги должны быть раздельными. `application.BuildMarkdownSite` вызывает admin/deployment перед активацией release; web только открывает готовый `root` и не требует `source` или прав записи. В `source/templates/` лежат общие HTML-шаблоны, обязателен `page.html`; front matter может выбрать другой шаблон через необязательное поле `template`. Шаблон получает `.Slug`, `.Title`, `.Description` и `.Content`; поддерживаемые поля front matter — `slug`, `title`, `description`, `template`, лишние поля и YAML-документы отклоняются.
- Slug — root-relative URL path; после нормализации он задаёт каталог страницы, а файл берётся из `pages.index` (`/` создаёт корневой index). Файлы `.md` и `.markdown` требуют YAML front matter со slug. Остальные regular files копируются с сохранением байтов; содержимое `templates/` в публикацию не попадает.
- Сборка ограничивает Markdown-файл 16 MiB, суммарный вход 1 GiB, один шаблон 1 MiB и набор шаблонов 16 MiB. Вывод собирается рядом с root и переключается rename-операциями только после успешной сборки; предыдущий root остаётся в скрытом backup-каталоге без автоматической очистки. Source/output с вложенными путями друг в друге запрещены.
- Для asset-пути сохраняется `Cache-Control` из конфигурации; `.well-known` и известные системные файлы обслуживаются из content root с `max-age=0`. При отсутствии custom 404-файла статус 404 сохраняется с пустым телом.

## Зависимости и проверенные источники

- Пользователь выбрал [go-markdown](https://github.com/osspkg/go-markdown); актуальная Go-документация: [pkg.go.dev/go.osspkg.com/markdown](https://pkg.go.dev/go.osspkg.com/markdown).
- Документация пакета `go.osspkg.com/markdown` v0.1.0 указывает требование Go 1.26+, raw HTML по умолчанию экранируется; стандартные лимиты — 16 MiB input, глубина 128 и 1,000,000 tokens. Сборщик использует пакетный лимит на вход, задаёт общий лимит релиза и не включает `WithUnsafeRawHTML`.
- Go `html/template` выбран пользователем для шаблонов. Шаблоны сайта следует считать доверенной частью конфигурации; значения front matter — недоверенным вводом.

## Низкорисковые предположения

- Slug нормализуется как URL-путь; дубликаты проверяются после нормализации.
- Для Markdown страницы `title`/`description` доступны в template data, но не обязательны.
- Файлы со скрытыми/резервными именами и симлинки из архива обрабатывает общий безопасный архивный слой F03.
